## NEW — 9. Six write-capable functions are callable by anyone, unauthenticated

Not previously recorded anywhere. These are `SECURITY DEFINER` (they run with owner rights)
and `VOLATILE`, and `anon` can execute them over PostgREST at `/rest/v1/rpc/<name>`:

| Function | Contains a write |
|---|---|
| `pb_attribute_orphan_calls(boolean)` | yes |
| `pb_contact_events_from_calls()` | yes |
| `pb_contact_events_from_gmail()` | yes |
| `pb_contact_events_from_quotes()` | yes |
| `pb_fathom_crawl_step(integer)` | yes |
| `pb_fathom_backfill_tick(integer)` | calls into the stepper |

**The mechanism is the same trap CLAUDE.md already documents for tables, never applied to
functions.** Their ACL reads `=X/postgres` — a leading `=` with no role name means EXECUTE was
granted to **PUBLIC**, which is Postgres's default for every new function. `anon` inherits it.
The file warns at length that "a new `pb_` table arrives with `anon` AND `authenticated`
holding everything" and that "every new table needs its own `revoke`, for both roles". Functions
need exactly the same thing and never got it.

This is an oversight, not a decision, and the contrast proves it: `pb_board` and `pb_dossier`
carry *explicit* `anon=X` grants — the two deliberate read functions from §43 — and
`pb_autoconfirm_facts` carries an explicit `authenticated=X`. The six above carry no explicit
grant at all, only the PUBLIC default.

It contradicts the stated posture directly: *"Never grant `anon` an insert, update or delete."*
A definer function that writes, executable by `anon`, is that grant laundered through a function.
The Fathom stepper also reaches external APIs through `pg_net`, so it is a quota and cost vector
as well as an integrity one.

**The fix is safe.** Neither page calls any of the six — `board.html` and `index.html` between
them use only `pb_board`, `pb_dossier`, `pb_dashboard`, `pb_confirm_fact_candidates`,
`pb_reject_fact_candidates`, `pb_review_candidate`, `pb_review_fact_candidate`,
`pb_merge_accounts`. `pg_cron` calls them as `postgres`/`service_role`, which a revoke from
PUBLIC does not touch.

    revoke execute on function
      public.pb_attribute_orphan_calls(boolean),
      public.pb_contact_events_from_calls(),
      public.pb_contact_events_from_gmail(),
      public.pb_contact_events_from_quotes(),
      public.pb_fathom_crawl_step(integer),
      public.pb_fathom_backfill_tick(integer)
    from public, anon;

Worth auditing every other `pb_` function the same way, not just these six, and adding a
function-grants check beside the table-grants check.
